# facility-security-risk-analytics

A data analytics dashboard that quantifies and visualizes **physical security
risk** across facility types, using a weighted multi-factor risk model.
Built as a portfolio project pairing domain expertise from physical security
/ safety risk assessment with data analytics and applied ML.

**Live:** [facility-security-risk-analytics.vercel.app](https://facility-security-risk-analytics.vercel.app) · API: [facility-security-risk-analytics-production.up.railway.app](https://facility-security-risk-analytics-production.up.railway.app) <!-- TODO: replace with the real URLs once deployed -->

See [`DEPLOY.md`](DEPLOY.md) for the deployment setup (Railway + Vercel).

> **All facility data in this repository is synthetic.** Every score,
> countermeasure flag, and outcome value is generated by
> `backend/app/risk/generate.py` — nothing is drawn from a real client, site,
> or incident. See [`data/README.md`](data/README.md).

## The risk model

Seven weighted factors, each scored 1-5 per facility:

| Factor | Weight |
|---|---|
| Asset criticality / value | 20% |
| Public accessibility | 15% |
| Perimeter vulnerability | 15% |
| Threat exposure | 15% |
| Existing countermeasures (inverse — reduces risk) | 20% |
| Site complexity | 10% |
| Response readiness | 5% |

The weighted average is rescaled to a **0-100 `risk_score`**. Full scoring
convention, including the countermeasures inversion, is documented in
[`backend/app/risk/config.py`](backend/app/risk/config.py) and
[`scoring.py`](backend/app/risk/scoring.py).

Four facility archetypes are modeled, each with its own realistic score
distribution (see `config.py` for the exact means/spreads and rationale):

1. **Cultural / heritage site** — high public access, high asset value,
   restricted modification options.
2. **Commercial retail complex** — very high public access, moderate asset
   value, large perimeter.
3. **Mixed-use tower** — moderate access, vertical security challenges, high
   asset density.
4. **Critical infrastructure** (substation / warehouse type) — low public
   access, very high asset criticality, remote/unstaffed risk.

## Layout

| Path | What lives here |
|---|---|
| `backend/` | `app/risk/` — risk scoring + synthetic data generator + prediction service. `app/api/` — the FastAPI routes. uv-managed. |
| `frontend/` | React + Vite + Tailwind dashboard (facility list, what-if detail view, archetype comparison). |
| `data/` | Synthetic dataset. **No real facility data.** |
| `notebooks/` | EDA, risk-score validation, interpretable ML + SHAP (outputs committed — see `notebooks/README.md`). |
| `models/` | Trained model artefact + precomputed SHAP summary (gitignored; see `models/README.md`). |

## Development

```bash
cd backend
uv sync
uv run python -m app.risk           # regenerate data/processed/facilities.csv
uv run jupyter lab                   # open notebooks/01-eda-risk-scoring.ipynb (trains + saves the models)
uv run uvicorn app.main:app --reload # serve the API at http://localhost:8000
```

```bash
cd frontend
npm install
npm run dev    # dashboard at http://localhost:5173, proxies /api to the backend
```

The API reads `data/processed/facilities.csv` and `models/incident_likelihood_model.joblib` /
`models/shap_summary.json`. These are committed (small, fully synthetic) so a fresh clone or a
deploy doesn't need to re-run the dataset generator or the notebook — but if you regenerate them
locally, re-run both commands above and commit the results.

## API

All routes are prefixed `/api`; `GET /health` (no prefix) is a bare liveness check.

| Route | Description |
|---|---|
| `GET /api/facilities` | List facilities. Optional `?archetype=` filter (one of the 4 archetype keys — an unknown value returns `422`). |
| `GET /api/facilities/{id}` | One facility's raw factors, flags, `risk_score`, and stored (synthetic) `incident_likelihood`. `404` if the id doesn't exist. |
| `POST /api/facilities/{id}/what-if` | Recompute risk under a partial override of factor scores and/or countermeasure flags — see below. |
| `GET /api/shap-summary` | Precomputed mean \|SHAP\| per feature from the notebook's GBM (not recomputed live). |

**`POST /api/facilities/{id}/what-if`** takes a partial override — any subset of the 7 factors
(each validated to `1 <= x <= 5`, `422` otherwise) and/or the 5 boolean flags — and returns the
`risk_score` plus **both** trained models' predicted `incident_likelihood`, before and after the
override, plus the delta:

```json
{
  "facility_id": "F001",
  "applied_overrides": {"factors": {"existing_countermeasures": 5.0}, "flags": {}},
  "before": {"risk_score": 75.96, "ridge_incident_likelihood": 62.82, "gbm_incident_likelihood": 59.74},
  "after":  {"risk_score": 57.11, "ridge_incident_likelihood": 34.86, "gbm_incident_likelihood": 38.58},
  "delta":  {"risk_score": -18.85, "ridge_incident_likelihood": -27.96, "gbm_incident_likelihood": -21.16}
}
```

**Why both models, not one:** Ridge has the better raw fit (R²=0.56 on the n=300 dataset) but is
structurally linear, so it can't represent the threat_exposure × existing_countermeasures
interaction built into the synthetic ground truth. The shallow GBM has a worse raw fit (R²=0.46)
but is the one that recovers that interaction — confirmed via the SHAP analysis in the notebook,
where `threat_exposure`'s importance rank rose from #4 to #2 once the dataset was scaled from 52
to 300 rows. Rather than picking a "winner," the API exposes both predictions side by side so the
accuracy-vs-interaction-capture tradeoff is a visible part of the dashboard, not a decision hidden
behind a single number.
